# Shared flash in 0.4.0

> Version 0.4.1 retains this layout/registry and adds a separate optional startup-target NVS key. Its short update image preserves shared app storage when used as documented; the full fresh image remains a separate, destructive artifact.

The owner approved a fresh storage layout. This replaces the fixed-slot design used through 0.3.1, and removes the community download helper. App installation uses local BIN upload only.

The verified 8 MiB layout reserves `0x0–0xffff` for boot/table/system areas, `0x10000–0x18ffff` for the resident factory launcher, and `0x7f0000–0x7fffff` for 64 KiB metadata NVS. The shared pool is `0x190000–0x7effff`: **6,684,672 bytes / 6.375 MiB**. No execution-slot duplicate or firmware repository is required; an installed image stays in its own allocated extent.

Each record owns an image extent rounded up to 4 KiB and a separate 128 KiB private NVS extent. Image starts retain the [ESP-IDF 64 KiB alignment requirement](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32c3/api-guides/partition-tables.html). An empty pool can allocate up to 6.25 MiB of image storage after one settings reservation, subject to image validity and address/memory constraints. This is a flash-budget calculation, not a physical execution claim. There is no arbitrary 2 MiB image limit. The bounded app index supports 16 identities, consistent with the SDK's 16 OTA subtypes; usual community app sizes exhaust flash earlier. Arbitrarily many firmware images are not promised.

The pure first-fit allocator searches free extents without moving another app or its data. Updates may reclaim/reallocate their own code and keep the same private-data address. New code is not bootable until complete SHA-256 and SDK image validation pass. Fragmentation may reduce the largest installable ROM below total free bytes. The device and portal report free bytes; `/api/capacity` also reports pool total, allocated bytes, installed payload bytes and the largest new ROM after its private-data reservation. Metadata-only `/api/preflight` validates allocation and ownership before code transfer; installation repeats those checks under the manager lock.

The v2 NVS registry records ownership, extents, initialization and lifecycle state. INSTALLING precedes any erase. New private storage is erased before READY; a retry repeats initialization until installation succeeds. An update preserves initialized settings. Full uninstall stores a non-bootable tombstone and marks private data uninitialized before code/data erasure, then frees ownership. Partial deletion can be retried safely. A failed metadata commit is re-read before allowing another allocation; an uncertain ownership state blocks further destructive work. Default-NVS community snapshots and their recovery journal remain identity-bound.

Factory boots expose only the permanent table entries. The launcher registers validated app/data extents with the ESP-IDF partition API. A one-use 32-byte RTC ticket carries the selected allocation and a checksum. The custom bootloader consumes and clears it before any table operation. It builds a temporary table containing factory/system/metadata and the selected app/data, with MD5 and readback verification, then boots that app as OTA 0. The native SDK identifies the app by its stable ID and exact running extent, rather than assuming a fixed slot address.

Every other reset reconstructs the permanent factory table **before the SDK attempts to parse it**. Thus an interrupted table erase/write returns to the factory-repair path; it does not rely on the damaged table to find the launcher. This guarantee assumes the resident bootloader and factory code are intact. USB ROM flashing and arbitrary raw-write firmware can still overwrite them. No secure boot, flash encryption, eFuse change or hardware isolation has been added.

A switch to an app and return to factory can each require one erase/program of the table sector. Identical tables are not rewritten. This increases flash wear compared with the old fixed table; endurance and actual power-cut behavior remain unverified. Application launch still verifies the exact installed hash, native identity/mode, one-use ticket and cold-start cancellation policy. Watchdog, panic and ordinary app restart enter the launcher.

SDK 1 binaries must be rebuilt using SDK 2, including its 32-byte custom RTC reservation; silently loading the old registry/address contract is refused. Community ESP-IDF 5.5.x app-only and supported standard merged images continue to work with no launcher SDK integration. Extra filesystem/resource partitions, incompatible flash settings or direct absolute-address assumptions still need an application port. Pokémon/app 1434 remain blocked by their custom partition dependencies even though their code fits an empty pool.

The full fresh-install BIN is explicitly padded to 8 MiB, clearing every old app/data/metadata region. This is intentional data loss approved for this migration. Do not use it as a settings-preserving update. Old 0.1–0.3 archives and migration guides describe historical layouts and must not be used as the 0.4 procedure.

Host validation covers >2 MiB streams, a fourth app with persistent private values, 10,000 allocation operations, capacity accounting, fragmentation, unrelated data preservation, metadata failures/retries, partial default-NVS writes and torn partition-table operations. The 48 KiB LVGL pool is tested with the full 16-entry library. ESP32 machine code, actual flash endurance and physical RF/heap/stack/power-cut behavior are not simulated by these tests.
